## 问题：一百万行里找一个 id

上一课把记录装进页，但按 `id` 查找仍可能从第一页一路扫到最后一页。假设每页容纳约 100 行，一百万行大约有一万页。即便数据已经按页组织，最坏情况下仍需检查一万页。

现在给每行附加一个额外结构，让我们能更快找到目标。这个结构必须能在数据插入、删除和更新后继续正确工作。

先自己想：若把所有 `(id, page_id)` 按 id 排序存起来，查询要读多少？插入一个新 id 又要做什么？

## 尝试一：有序数组

若有序数组完整地放在内存中，二分查找只需约 `log₂(N)` 次比较；一百万个键大约 20 次比较。但磁盘上的数组不能把“比较次数”直接等同于“读页次数”：相邻比较可能落在不同页。更麻烦的是，插入新键可能要移动大量后续条目；即使采用追加与重写，也要处理崩溃中断和空间增长。

因此我们需要的不是仅仅“能排序”的结构，而是：

- 查找时尽量减少随机页访问；
- 插入、删除时只改动有限的页面；
- 页面能装下很多键，树的高度足够低；
- 结构在崩溃或并发修改下仍能恢复到合法状态（这是后续课程要补上的问题）。

## 发现：用页做多路导航

二叉树每个节点只有两个分支。若一个节点本身就是磁盘页，一页可以容纳许多分隔键，于是一次页读取就能在大量范围中选出下一页。

以键 `42` 为例，一个内部页可保存边界键 `[20, 50, 80]` 和四个子页指针：

```text
        [20 | 50 | 80]
       /     |     |     \
   <20   20..50  50..80   >=80
```

每层把搜索范围缩小很多。若分支数近似为 `b`，树高大致随 `log_b(N)` 增长。分支数越大，树通常越矮；实际可容纳的键数受页大小、键宽度、指针/槽目录和填充率影响。

把有序键组织在多路平衡树中，常见结果是 **B 树家族**。数据库常使用 **B+ 树**风格：内部页负责导航，叶子页保存键与行定位信息，并按键顺序连接或可顺序遍历。这样点查能从根走到叶子，范围查询则可从起始叶子向后扫描。

## 概念：索引保存什么

索引是一种辅助访问路径。它把搜索键映射到行本身，或映射到能够找到行的位置。索引不是数据的免费副本：每次影响索引键的写入，也要维护索引结构。

以表 `users(id, email, name)` 为例，可以有：

```text
主键索引：id → 行
二级索引：email → 行定位信息
```

若 `email` 的索引叶子保存主键 `id`，通过邮箱查到 id 后还可能再用主键查一次行。这种“两次定位”的具体行为取决于数据库和表组织方式，后续会分别看 InnoDB 与 PostgreSQL，不能把它视为所有索引的固定规则。

## 推导：点查与范围查是不同能力

对 `WHERE id = 42`，索引沿内部页导航到对应叶子，再取目标记录。

对 `WHERE id BETWEEN 100 AND 200`，树先找到 100 所在叶子，再按键序向后扫描，直到超过 200。若查询还要返回 `name`，索引里没有 `name` 时可能要为范围中的每一行回表。

这说明索引是否有用取决于完整访问路径：

```sql
SELECT name FROM users WHERE id BETWEEN 100 AND 200;
```

如果查询范围很大，回表的随机访问可能比顺序扫描整张表更贵。优化器需要估算两种计划的成本；“有索引”并不意味着“必然使用索引”。

## 新压力：索引让读更快，写为何更贵？

插入一行时，需要找到叶子位置并插入键。若页满了，就要分裂页面、调整父页，必要时向上分裂。删除也会留下空闲空间，合并或再平衡会带来额外工作。更新索引列通常相当于删旧键、插新键。

因此额外索引会增加：

- 磁盘空间与缓存占用；
- 插入、删除和索引列更新的工作量；
- 日志量、写放大和恢复需要处理的变更；
- 优化器需要比较的访问路径。

索引设计是在读收益和写/空间成本之间取舍。索引越多不一定越快。

## 实验：估算树高与回表成本

做一组纸上估算，明确这只是简化模型：

1. 页大小 16 KiB，页头和槽目录以外可用于索引项的空间设为 12 KiB。
2. 每个内部索引项（分隔键加子页指针）平均 32 字节。
3. 估算每个内部页能容纳多少分支，再估算十亿个键的理想树高。
4. 若一次范围查返回 5000 行，二级索引只保存键和主键，且每行还需一次随机访问数据页，判断这条索引路径可能输给全表扫描的原因。

不要把结果当成真实数据库的精确树高：页填充率、键长分布、页头开销、缓存命中、压缩和实现细节都会改变答案。模型的价值是让你看见“分支数降低高度”和“回表造成随机 I/O”这两个压力。

## 实现对照：之后要验证的问题

在 MySQL 8/InnoDB 中，主键组织方式会影响二级索引定位；在 PostgreSQL 中，heap 表与索引的关系又不同。两者都提供 B-tree 索引访问方法，但页组织、并发、可见性与回表路径并非同一套实现。

在继续之前，先把这些作为待验证的问题，而不是记成结论：

1. 二级索引叶子到底保存什么？
2. 主键行移动/更新会不会影响二级索引？
3. 索引扫描怎样处理 MVCC 可见性？
4. 页分裂如何与并发写入及崩溃恢复配合？

这些问题会在引擎对照、MVCC 和恢复章节逐个解决。具体版本的实现事实将引用对应版本的官方文档或源码。

## 练习

### 1. 访问路径

有索引 `(last_name, first_name)`。判断下面查询是否能从索引有序范围开始定位，并解释理由：

```sql
WHERE last_name = 'Li' AND first_name = 'Ming'
WHERE last_name = 'Li'
WHERE first_name = 'Ming'
WHERE last_name >= 'L' AND first_name = 'Ming'
```

重点描述键的字典序和可确定的前缀范围，不要只背“最左前缀”四个字。

### 2. 选择题要给理由

一个只读分析任务每天扫描全表一次，一个在线服务频繁按 `status` 更新、偶尔按 `status` 查询，而 `status` 只有三个可能值。分别讨论是否值得建索引。你还需要哪些统计信息和负载数据才能做决定？

## 本章小结（完成重建后再看）

```text
全表扫描读页太多
  → 需要辅助访问路径
  → 有序结构支持定位和范围查询
  → 磁盘页做多路节点能降低树高
  → B+ 树叶子保持有序，适合范围扫描
  → 插入/删除要维护树，索引增加空间和写放大
  → 查询优化器要比较索引路径与扫描路径
  → 页分裂、并发与崩溃恢复成为新问题
```
