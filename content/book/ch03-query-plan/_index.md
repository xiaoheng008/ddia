## 问题：同一句查询，为什么可能快慢悬殊？

假设有两张表：一张保存订单，一张保存用户。我们想找出某城市用户在指定时间段内的订单：

```sql
SELECT u.name, o.total
FROM users AS u
JOIN orders AS o ON o.user_id = u.id
WHERE u.city = 'Hangzhou'
  AND o.created_at >= '2026-01-01';
```

SQL 描述了结果应该是什么，却没有写明先读哪张表、走哪个索引、用什么方式连接、数据放不进内存时怎样处理。数据库必须把声明转换成一系列可执行步骤。

## 尝试：把查询步骤写死

一种直觉方案是：先扫描 `users` 找杭州用户；对每个用户，去 `orders` 查这个用户在时间条件内的订单。

这个方案可以工作。但如果杭州用户占全体用户的 90%，逐个查订单可能产生大量随机访问；反过来，如果订单表里最近日期只占很小部分，也许先筛订单更合适。若用户很多、订单极少，先从订单出发可能少做得多。

我们发现：SQL 的书写顺序不是必须执行顺序。执行顺序应利用表大小、过滤条件、索引和数据分布来选择。

## 观察：查询可以拆成关系操作

先不谈具体实现，把查询拆成这些逻辑操作：

```text
读取 users 与 orders
  → 按 city 和 created_at 过滤
  → 按 users.id = orders.user_id 匹配行
  → 只保留 name 和 total 两列
```

这里表达的是“要做什么”，而不是“每一步怎样访问磁盘”。它类似代数表达式：过滤、投影、连接等关系运算可以按满足语义的规则变换。例如过滤条件可以尽早执行，减少后续步骤要处理的行数。

这类表示称为**逻辑计划**。它让数据库能推理查询含义，同时不受某一种索引或连接算法绑死。

## 新压力：逻辑上等价，物理成本不同

有了逻辑计划，我们仍需选择执行方法。比如连接两个输入时，常见策略包括：

### 嵌套循环连接

对左侧每一行，到右侧寻找匹配行。若右侧有合适索引，内层查找可很便宜；若两边都很大且内层反复全扫，工作量会接近两边行数的乘积。

```text
for each row in left:
    find matching rows in right
```

### 哈希连接

对一个输入按连接键建立哈希表，再扫描另一个输入查找匹配。它通常适合等值连接，并且需要内存；若哈希表放不下，就可能分批处理并产生临时 I/O。

### 归并连接

若两边按连接键有序，可同步向前扫描并匹配相同键。排序本身有成本；若输入已经由索引提供顺序，归并过程可能很有吸引力。

这些不是“谁永远最快”的竞赛。适用性取决于输入规模、是否有序、索引、内存和数据分布。

从逻辑操作选择具体扫描和连接方法，得到**物理计划**。物理计划才具体到顺序扫描、索引扫描、哈希连接、排序等算子。

## 概念：优化器是在候选计划间做估算

查询优化器通常先应用保持语义的改写规则，再生成若干候选物理计划，并用代价估算挑选计划。一个简化代价模型可能考虑：

- 预计要读多少页，以及顺序读还是随机读；
- 过滤后大约剩多少行；
- 比较、哈希、排序要消耗多少 CPU 和内存；
- 中间结果是否会溢出到磁盘；
- 并行执行的收益和协调成本。

优化器面对的是估算，不是提前知道真实运行时间。它依赖表与索引统计信息，例如行数、不同键值数、直方图和数据页数。统计信息陈旧或分布高度偏斜时，估算可能严重偏离实际。

## 推导：为什么错误估算会改变整条计划

考虑一个过滤谓词，估计它会留下 1% 的行：

```text
扫描输入 → 过滤 → 用较小结果建哈希表 → 连接
```

若真实选择率是 80%，哈希表可能比预计大得多，甚至溢出；若优化器低估了过滤后的行数，它也可能选择大量重复索引查找，实际成本超过一次顺序扫描。

因此优化器的问题不只是“有没有索引”，而是：

1. 这个谓词预计能过滤多少行？
2. 访问这些行要读多少页？
3. 选择这一边作为哈希构建输入，内存够不够？
4. 统计信息能否代表当前数据分布？

## 实验：手工比较两种连接顺序

不用运行数据库，先用纸笔推理。假设：

- `users` 有 100 万行，`city='Hangzhou'` 预计命中 2 万行；
- `orders` 有 1 亿行，最近日期的过滤预计命中 100 万行；
- `orders.user_id` 有索引，`users.id` 是唯一键；
- 每次读取数据页都有成本，随机读取通常比连续扫描更贵。

分别比较：

**计划 A**：先找 2 万个用户，再对每个用户用 `user_id` 索引查订单并过滤日期。

**计划 B**：先找 100 万条近期订单，再通过用户主键查用户并过滤城市。

暂时忽略实现细节，估算哪个计划更可能合适。接着改变一个条件：如果杭州用户只有 20 个，或近日期订单有 5000 万条，你的结论会怎样变化？

这个练习刻意不追求一个固定答案：索引覆盖情况、聚簇顺序、缓存和键分布都会影响真实成本。重点是识别计划依赖的假设。

## 观察真实数据库：读计划，不只看 SQL

`EXPLAIN` 一类工具会展示数据库为查询选择的计划。不同系统的输出格式不同，但通常值得逐层问：

- 从哪张表开始？扫描方式是什么？
- 哪些过滤条件在扫描时执行，哪些在之后执行？
- 两输入通过什么连接算法组合？
- 估算行数在哪里明显膨胀或缩小？
- 是否有排序、临时结果或可能溢出的操作？
- 如果能查看实际执行统计，估算行数与实际行数从哪里开始分叉？

估算计划不等于实际运行轨迹。具体数据库版本的 `EXPLAIN` 选项、执行统计和计划字段会不同；实践时应查对应版本文档。执行计划用于解释数据库的选择，不能单独证明某条查询在所有数据和缓存状态下都更快。

## 新问题：计划正确，事务语义如何保证？

优化器能重排过滤、连接等操作，但变换必须保持 SQL 语义。遇到 `NULL`、外连接、聚合、子查询或易变函数时，并不是任意交换都安全。

即使计划逻辑正确，执行期间数据可能被其他事务修改。系统还需要定义查询读取哪个时间点的数据，以及并发更新怎样与读取协调。由此进入事务隔离、锁与 MVCC。

## 练习

### 1. 哪些地方可以改变顺序？

两个内连接的关系可以在满足条件时改变连接顺序。请举一个外连接例子，说明为什么简单交换左右输入可能改变结果。试着用一行输入为空、另一行有匹配行的情况构造反例。

### 2. 低选择率与高选择率

一个布尔列 `is_active` 中 99% 的行都是 `true`。分别讨论查询 `is_active = true` 和 `is_active = false` 时，普通 B+ 树索引可能有多大帮助。再说明如果表的物理排列或索引覆盖情况不同，结论怎样变化。

### 3. 估算偏差

某连接输入被估为 100 行，实际有 500 万行。列出两种可能被选中但最终代价很高的执行选择，并说明计划中哪些估算信号能帮助定位问题。

## 重建题

从“SQL 写出结果条件，却没指定访问步骤”开始，解释为什么需要逻辑计划；再说明为什么逻辑计划仍不足以执行查询；最后推出物理计划和代价估算的角色。给出一个统计信息不准导致坏计划的例子，并指出优化器要保持哪些语义不变。

## 本章小结（完成重建后再看）

```text
SQL 声明要什么，不规定执行顺序
  → 关系运算表示查询含义（逻辑计划）
  → 多种扫描/连接方式都可能满足同一逻辑
  → 选择具体算子得到物理计划
  → 统计信息估算候选计划的资源成本
  → 估算偏差会造成不合适的计划
  → 执行仍须遵守 SQL 语义和事务可见性
```
