# 第一课：从文件到存储页

## 问题

假设要保存一张用户表：`(id, name, email)`。进程重启后数据必须还在；用户按 `id` 查找，也会按邮箱查找。先不借用数据库，设计最小可工作的存储方式。

写下三个约束：

1. 一百万条记录如何定位其中一条？
2. 更新一条记录时，进程恰好崩溃，重启后允许看到什么？
3. 两个请求同时改同一行，怎样避免相互覆盖？

先不要引入 B+ 树、WAL 或事务这些名字。它们应当是后面由失败案例推出的答案。

## 尝试：追加记录

最简单的做法是把每条记录编码后追加到文件末尾。插入很直接，扫描也容易；查询特定 `id` 却需要从头读到尾。若每次都扫描，记录数扩大十倍，最坏查询工作量也大约扩大十倍。

可以维护 `id → 文件偏移` 的内存字典，但重启后字典消失；把字典也写盘，则字典本身又需要查找、更新和恢复。我们并未消除问题，只是把它移到了另一份结构里。

## 发现：磁盘读写有单位

存储设备和操作系统通常按块搬运数据。若每次只为一行发起一次随机读，固定寻址成本可能比处理这行数据更贵。因此存储引擎把多条记录放进固定大小的页，并以页作为缓冲、读写和恢复的基本单位。

这给出第一个抽象：**页**。页内还需要管理空闲空间、记录位置和删除后的空洞；记录也可能跨页或变长。页并不自动解决查找问题，但它让磁盘 I/O、内存缓存和数据布局有了共同单位。

## 小实验：页内槽目录

纸上设计一个 4096 字节页：页头占 64 字节，每条记录变长。若记录内容从页尾向前放，槽目录从页头向后增长，页头保存两者边界，就能通过槽号定位记录，并在一定程度上移动记录而保持槽号稳定。

思考：删除一条记录后，是立刻搬动后续记录，还是留下空洞？前者让页内偏移变化，后者要处理空间碎片。真实实现会在稳定引用、空间利用和写入成本之间取舍。

## 下一道压力

页减少了 I/O 的粒度，却没有让 `id` 查找变快：仍然可能要逐页扫描。下一课从“怎样少读页”推出索引，并比较索引带来的写入与空间成本。

## 重建题

不用看正文，从“追加文件的查找为什么变慢”开始，解释页为什么出现，以及页为什么还不足以解决快速查找。再指出把内存字典写到磁盘后，哪些持久化问题仍然存在。
